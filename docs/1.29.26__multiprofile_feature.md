## 1. Executive Summary

### Goal

Transform Health Tracker 9000 from single-profile to multi-profile architecture, enabling household members (parents, children, etc.) to maintain separate health tracking data while sharing a single installation.

### Key Constraints

- **Security**: Profile data (age, weight, height, gender, health conditions, allergies) MUST remain in JSON files, NEVER in database
- **Simplicity**: No authentication/login required (local-first app)
- **Data Isolation**: Each profile's meals, supplements, calorie tracking, and weight logs must be completely separate
- **Backward Compatibility**: Existing single-profile data must migrate cleanly

### Scope

- Add profile selection and switching UI
- Implement multi-profile storage in JSON
- Filter all database queries by active profile_id
- Provide smooth onboarding for new profiles
- Migrate existing single-profile installations

## 2. Problem Statement

### Current Behavior

1. User types a profile name during onboarding (e.g., "MC")
2. System checks if `data/profile.json` exists
3. If exists: Updates `displayName` field but keeps original profile ID (e.g., "jb-dad8158b")
4. If new: Creates profile with new ID based on displayName

### User Confusion

- Users expect typing "MC" to create a NEW profile for their child
- Instead, it updates dad's profile display name to "MC"
- No UI shows which profile is active
- No way to switch between family members
- Database has `profile_id` foreign keys but no actual isolation

### Example Scenario

```
Family: Dad (JB), Mom, Child (MC)
Current: Only ONE profile exists at a time
Expected: Three separate profiles with independent data
```

### Profile ID Generation

**File**: `src/lib/database/repositories/profileRepository.ts`

```typescript
private generateProfileId(displayName?: string): string {
  const name = displayName || 'user';
  const timestamp = Date.now();
  const hash = crypto.createHash('md5')
    .update(`${name}-${timestamp}`)
    .digest('hex')
    .substring(0, 8);
  return `${name.toLowerCase().replace(/\\s+/g, '-')}-${hash}`;
}
```

**Format**: `{displayName}-{8-char-hash}`  
**Example**: `jb-dad8158b`, `mom-a3c4e1f9`, `mc-5b2d7f1a`

## 4. Proposed Solution

### High-Level Approach

**Multi-file JSON storage** with session-based active profile tracking.

### Architecture Decision: Option B - Multiple Profile Files

#### Option A: Single File with Array ❌

```json
{
  "version": "2.0",
  "profiles": [
    { "id": "jb-dad8158b", "displayName": "Dad", ... },
    { "id": "mom-a3c4e1f9", "displayName": "Mom", ... }
  ],
  "activeProfileId": "jb-dad8158b"
}
```

**Cons**:

- Entire file rewritten on every profile update
- Harder to debug individual profiles
- Greater risk of corruption affecting all profiles

#### Option B: Multiple Profile Files ✅ **RECOMMENDED**

```
data/
  profiles/
    jb-dad8158b.json        # Dad's profile
    mom-a3c4e1f9.json       # Mom's profile
    mc-5b2d7f1a.json        # Child's profile
  active-profile.json       # Points to active profile ID
```

**Pros**:

- Each profile is independent file (easier backup/restore)
- Atomic writes per profile (less corruption risk)
- Easier to debug (one file per person)
- Natural fit for import/export individual profiles
- Aligns with security constraint (JSON files only)

**File Structure**:

```typescript
// data/profiles/{profileId}.json
{
  "id": "jb-dad8158b",
  "displayName": "Dad",
  "age": 45,
  "weight": 85,
  "height": 180,
  "gender": "male",
  "activityLevel": "moderate",
  "healthConditions": ["gout"],
  "allergies": ["shellfish"],
  "createdAt": "2026-01-20T10:00:00.000Z",
  "updatedAt": "2026-01-29T15:30:00.000Z"
}

// data/active-profile.json
{
  "activeProfileId": "jb-dad8158b",
  "lastSwitched": "2026-01-29T15:30:00.000Z"
}
```

### Profile Repository Changes

**File**: `src/lib/database/repositories/profileRepository.ts`

#### New Methods

```typescript
export class ProfileRepository {
  private PROFILES_DIR = path.join(process.cwd(), 'data', 'profiles');
  private ACTIVE_PROFILE_PATH = path.join(process.cwd(), 'data', 'active-profile.json');

  // Core CRUD for multi-profile
  listProfiles(): UserProfile[];
  getProfileById(profileId: string): UserProfile | null;
  getActiveProfile(): UserProfile | null;
  setActiveProfile(profileId: string): void;
  createProfile(profile: Omit<UserProfile, 'id' | 'createdAt' | 'updatedAt'>): UserProfile;
  updateProfileById(profileId: string, updates: Partial<UserProfile>): UserProfile;
  deleteProfile(profileId: string): void;

  // Migration helpers
  migrateFromSingleProfile(): void;
}
```

#### Implementation Details

```typescript
listProfiles(): UserProfile[] {
  this.ensureProfilesDirectory();
  const files = fs.readdirSync(this.PROFILES_DIR);
  return files
    .filter(f => f.endsWith('.json'))
    .map(f => {
      const data = fs.readFileSync(path.join(this.PROFILES_DIR, f), 'utf-8');
      return JSON.parse(data) as UserProfile;
    })
    .sort((a, b) => a.displayName.localeCompare(b.displayName));
}

getActiveProfile(): UserProfile | null {
  const activeData = this.getActiveProfileData();
  if (!activeData?.activeProfileId) return null;
  return this.getProfileById(activeData.activeProfileId);
}

setActiveProfile(profileId: string): void {
  const profile = this.getProfileById(profileId);
  if (!profile) throw new Error(`Profile ${profileId} not found`);

  const activeData = {
    activeProfileId: profileId,
    lastSwitched: new Date().toISOString()
  };
  fs.writeFileSync(this.ACTIVE_PROFILE_PATH, JSON.stringify(activeData, null, 2));
}
```

### Migration Strategy

```typescript
migrateFromSingleProfile(): void {
  const oldPath = path.join(process.cwd(), 'data', 'profile.json');

  // Check if old single profile exists
  if (!fs.existsSync(oldPath)) return;

  const oldProfile = JSON.parse(fs.readFileSync(oldPath, 'utf-8'));

  // Create profiles directory
  this.ensureProfilesDirectory();

  // Move old profile to new location
  const newPath = path.join(this.PROFILES_DIR, `${oldProfile.id}.json`);
  fs.writeFileSync(newPath, JSON.stringify(oldProfile, null, 2));

  // Set as active profile
  this.setActiveProfile(oldProfile.id);

  // Rename old file (keep backup)
  fs.renameSync(oldPath, path.join(process.cwd(), 'data', 'profile.json.backup'));

  console.log('[Migration] ✅ Migrated profile from profile.json to profiles/');
}
```

## 7. Data Isolation Strategy

### 7.1 Database Query Filtering

**Current Problem**: Queries don't filter by `profile_id`

**Example - Current Code**:

```typescript
// src/lib/database/repositories/mealLogRepository.ts
getMealLogsByDate(date: string): MealLog[] {
  const stmt = db.prepare(`
    SELECT * FROM meal_logs
    WHERE date(meal_date) = date(?)
    ORDER BY created_at DESC
  `);
  return stmt.all(date).map(mapRowToMealLog);
}
```

**Fixed - With Profile Isolation**:

```typescript
getMealLogsByDate(date: string, profileId: string): MealLog[] {
  const stmt = db.prepare(`
    SELECT * FROM meal_logs
    WHERE date(meal_date) = date(?)
      AND profile_id = ?
    ORDER BY created_at DESC
  `);
  return stmt.all(date, profileId).map(mapRowToMealLog);
}
```

### 7.2 Repository Pattern Update

#### Strategy 1: Pass profileId to Every Method ❌

**Cons**: Breaks existing API, many changes required

#### Strategy 2: Constructor-Level Profile Context ✅ **RECOMMENDED**

```typescript
export class MealLogRepository {
  private profileId: string;

  constructor(profileId: string) {
    this.profileId = profileId;
  }

  getMealLogsByDate(date: string): MealLog[] {
    const stmt = db.prepare(`
      SELECT * FROM meal_logs 
      WHERE date(meal_date) = date(?) 
        AND profile_id = ?
      ORDER BY created_at DESC
    `);
    return stmt.all(date, this.profileId).map(mapRowToMealLog);
  }

  addMealLog(meal: Omit<MealLog, 'id'>): MealLog {
    const row = {
      id: crypto.randomUUID(),
      profile_id: this.profileId, // Auto-injected
      meal_date: meal.date,
      meal_type: meal.mealType,
      foods: JSON.stringify(meal.foods),
      created_at: new Date().toISOString(),
    };
    // ... insert logic
  }
}
```

**Benefits**:

- Clean separation of concerns
- profileId automatically injected into all queries
- Easier testing (mock constructor)
- Minimal changes to existing method signatures

interface ProfileState {
  // State
  activeProfile: UserProfile | null;
  profiles: UserProfile[];
  isLoading: boolean;
  error: string | null;

  // Actions
  fetchProfiles: () => Promise<void>;
  fetchActiveProfile: () => Promise<void>;
  switchProfile: (profileId: string) => Promise<void>;
  createProfile: (profile: Omit<UserProfile, 'id' | 'createdAt' | 'updatedAt'>) => Promise<void>;
  updateProfile: (profileId: string, updates: Partial<UserProfile>) => Promise<void>;
  deleteProfile: (profileId: string) => Promise<void>;
}

export const useProfileStore = create<ProfileState>((set, get) => ({
  activeProfile: null,
  profiles: [],
  isLoading: false,
  error: null,

  fetchProfiles: async () => {
    set({ isLoading: true, error: null });
    try {
      const res = await fetch('/api/profiles');
      const data = await res.json();
      set({ profiles: data, isLoading: false });
    } catch (err: any) {
      set({ error: err.message, isLoading: false });
      toast.error('Failed to fetch profiles');
    }
  },

  switchProfile: async (profileId: string) => {
    set({ isLoading: true });
    try {
      await fetch('/api/profiles/active', {
        method: 'PUT',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ profileId }),
      });

      // Reload active profile
      await get().fetchActiveProfile();

      // Clear all cached health data (force refetch for new profile)
      useHealthStore.getState().clearCache();

      toast.success('Profile switched successfully');
    } catch (err: any) {
      set({ error: err.message, isLoading: false });
      toast.error('Failed to switch profile');
    }
  },

  // ... other actions
}));
```

// src/app/api/profiles/[id]/route.ts
export async function DELETE(request: Request, { params }: { params: { id: string } }) {
  return withErrorHandling(async () => {
    const { id } = params;

    const repo = new ProfileRepository();
    const active = repo.getActiveProfile();

    // Prevent deleting active profile
    if (active?.id === id) {
      return NextResponse.json(
        { error: 'Cannot delete active profile. Switch to another profile first.' },
        { status: 400 }
      );
    }

    repo.deleteProfile(id);
    return NextResponse.json({ success: true });
  }, 'DELETE /api/profiles/:id');
}
```

### 11.1 Edge Cases

deleteProfile: async (profileId: string) => {

#### Case 2: Deleting Active Profile

**Scenario**: User tries to delete currently active profile

**Solution**:

- Prevent deletion
- Force user to switch first
- Error: "Cannot delete active profile. Switch to another profile first."

#### Case 3: Profile with No Data

**Scenario**: User creates profile but never logs data

**Solution**:

- Allow deletion without warning
- Show "empty profile" badge in UI
- Optional: Auto-delete profiles with 0 activity after 30 days

#### Case 4: Corrupted Profile File

**Scenario**: profile JSON file is malformed

**Solution**:

```typescript
getProfileById(profileId: string): UserProfile | null {
  try {
    const filePath = path.join(this.PROFILES_DIR, `${profileId}.json`);
    if (!fs.existsSync(filePath)) return null;

    const data = fs.readFileSync(filePath, 'utf-8');
    const profile = JSON.parse(data);

    // Validate schema
    return ProfileSchema.parse(profile);
  } catch (error) {
    console.error(`Corrupted profile file: ${profileId}`, error);
    // Move to quarantine folder
    this.quarantineCorruptedProfile(profileId);
    return null;
  }
}
```

#### Case 5: Two Users Edit Same Profile Simultaneously

**Scenario**: (Unlikely in local-first app, but possible if file synced via cloud)

**Solution**:

- Last write wins (acceptable for local-first)
- Optional: File-based locking (overkill for MVP)
- Document limitation: "Not designed for concurrent multi-user access"

### 11.2 Database Record Cleanup

#### Scenarios Requiring Cleanup

**Profile Deletion**:

- User deletes profile "MC"
- Database still has `meal_logs`, `supplement_logs`, etc. with `profile_id = "mc-5b2d7f1a"`

**Options**:

##### Option A: Soft Delete (Keep Orphaned Records) ✅ **RECOMMENDED**

```typescript
deleteProfile(profileId: string): void {
  // Only delete profile JSON file
  const filePath = path.join(this.PROFILES_DIR, `${profileId}.json`);

  // Archive profile before deletion
  const archivePath = path.join(this.PROFILES_DIR, 'archived', `${profileId}.json`);
  fs.renameSync(filePath, archivePath);

  // Database records remain (orphaned but queryable)
  // Benefit: Can restore profile with all historical data
}
```

**Pros**:

- Data never truly lost (easier recovery)
- Simple implementation
- Archive folder acts as backup

**Cons**:

- Database grows over time with orphaned records
- May need cleanup job eventually

##### Option B: Hard Delete (Cascade)

```typescript
deleteProfile(profileId: string): void {
  // Delete profile file
  const filePath = path.join(this.PROFILES_DIR, `${profileId}.json`);
  fs.unlinkSync(filePath);

  // Delete all database records
  const db = getDatabase();
  const tables = [
    'meal_logs',
    'supplement_logs',
    'calorie_tracking',
    'weight_logs',
    'daily_summary'
  ];

  tables.forEach(table => {
    db.prepare(`DELETE FROM ${table} WHERE profile_id = ?`).run(profileId);
  });
}
```

**Pros**:

- Clean database
- No orphaned records

**Cons**:

- Data permanently lost
- More complex implementation
- Risky if user deletes by accident

**Recommendation**: Use Option A (soft delete) for MVP, add hard delete as admin feature later.

### 11.3 Migration from Single Profile

#### Detection

```typescript
export function needsMigration(): boolean {
  const oldPath = path.join(process.cwd(), 'data', 'profile.json');
  const newDir = path.join(process.cwd(), 'data', 'profiles');

  return fs.existsSync(oldPath) && !fs.existsSync(newDir);
}
```

#### Migration Process

```typescript
export function migrateToMultiProfile(): { success: boolean; profileId: string } {
  console.log('[Migration] Starting multi-profile migration...');

  const oldPath = path.join(process.cwd(), 'data', 'profile.json');

  // 1. Read old profile
  const oldProfile = JSON.parse(fs.readFileSync(oldPath, 'utf-8'));
  console.log('[Migration] Found profile:', oldProfile.id);

  // 2. Create profiles directory
  const profilesDir = path.join(process.cwd(), 'data', 'profiles');
  fs.mkdirSync(profilesDir, { recursive: true });

  // 3. Write to new location
  const newPath = path.join(profilesDir, `${oldProfile.id}.json`);
  fs.writeFileSync(newPath, JSON.stringify(oldProfile, null, 2));
  console.log('[Migration] Created:', newPath);

  // 4. Set as active profile
  const activePath = path.join(process.cwd(), 'data', 'active-profile.json');
  fs.writeFileSync(
    activePath,
    JSON.stringify(
      {
        activeProfileId: oldProfile.id,
        lastSwitched: new Date().toISOString(),
      },
      null,
      2
    )
  );
  console.log('[Migration] Set active profile:', oldProfile.id);

  // 5. Archive old file (keep for safety)
  const backupPath = path.join(process.cwd(), 'data', 'profile.json.backup');
  fs.renameSync(oldPath, backupPath);
  console.log('[Migration] Archived old file:', backupPath);

  console.log('[Migration] ✅ Migration complete!');

  return { success: true, profileId: oldProfile.id };
}
```

#### Migration Trigger

**Strategy 1: On App Start**

```typescript
// src/app/layout.tsx or middleware
useEffect(() => {
  const repo = new ProfileRepository();
  if (repo.needsMigration()) {
    const result = repo.migrateToMultiProfile();
    toast.success(`Profile migrated successfully! Now using multi-profile system.`);
  }
}, []);
```

**Strategy 2: API Middleware**

```typescript
// src/app/api/profiles/route.ts
export async function GET() {
  const repo = new ProfileRepository();

  // Auto-migrate on first profiles access
  if (repo.needsMigration()) {
    repo.migrateToMultiProfile();
  }

  const profiles = repo.listProfiles();
  return NextResponse.json(profiles);
}
```

**Recommendation**: Use Strategy 1 (on app start) for user visibility.

### 11.4 Rollback Strategy

If migration fails or user wants to revert:

```typescript
export function rollbackToSingleProfile(profileId: string): void {

  // (User can manually delete profiles/ directory if needed)

}
```

## 13. Risk Assessment

### Technical Risks

#### Risk 1: File System Race Conditions

**Severity**: Medium  
**Likelihood**: Low  
**Description**: Multiple processes writing to same profile file simultaneously

**Mitigation**:

- Document that app is single-instance local-first
- If cloud sync needed, implement file locking
- Use atomic writes (write to temp file, then rename)

#### Risk 2: Data Corruption During Migration

**Severity**: High  
**Likelihood**: Low  
**Description**: Migration fails, user loses profile data

**Mitigation**:

- Always backup old profile.json before migration
- Test migration extensively
- Provide rollback mechanism
- Log all migration steps for debugging

#### Risk 3: Profile Switching Performance

**Severity**: Low  
**Likelihood**: Low  
**Description**: Switching profiles is slow (fetches all data)

**Mitigation**:

- Cache previous profile data (don't clear immediately)
- Add loading indicator during switch
- Optimize API calls (parallel fetching)
- Lazy load non-critical data

#### Risk 4: Database Query Performance

**Severity**: Low  
**Likelihood**: Low  
**Description**: Adding profile_id filters degrades query speed

**Mitigation**:

- Ensure profile_id column is indexed
- Test with large datasets (1000+ meals per profile)
- Monitor query performance

```sql
CREATE INDEX idx_meal_logs_profile_id ON meal_logs(profile_id);
CREATE INDEX idx_supplement_logs_profile_id ON supplement_logs(profile_id);
-- Add indexes for all tables
```

### User Experience Risks

#### Risk 5: User Confusion After Migration

**Severity**: Medium  
**Likelihood**: Medium  
**Description**: Users don't understand new multi-profile system

**Mitigation**:

- Show one-time tutorial after migration
- Toast notification explaining changes
- Add "What's New" modal
- Clear UI indicators for active profile

#### Risk 6: Accidental Profile Deletion

**Severity**: High  
**Likelihood**: Medium  
**Description**: User deletes wrong profile, loses data

**Mitigation**:

- Soft delete (archive) by default
- Confirmation dialog with profile name
- "Undo delete" within 30 days
- Export data before deletion

#### Risk 7: Profile Switching Confusion

**Severity**: Low  
**Likelihood**: Medium  
**Description**: User logs data to wrong profile by accident

**Mitigation**:

- Prominent active profile indicator
- Profile avatar/color coding
- Confirmation when switching profiles
- Recent activity shows profile name

### Security/Privacy Risks

#### Risk 8: Profile Data Exposure

**Severity**: High  
**Likelihood**: Low  
**Description**: Profile data leaks between profiles in UI

**Mitigation**:

- Comprehensive testing of data isolation
- Clear healthStore cache on switch
- Verify all queries filter by profile_id
- Add E2E isolation tests

#### Risk 9: File System Permissions

**Severity**: Medium  
**Likelihood**: Low  
**Description**: Profile files readable by other users on shared computer

**Mitigation**:

- Set restrictive file permissions (0600)
- Document: "This app is designed for trusted environments"
- Optional: Add password protection per profile (future enhancement)
